A framework for any system design

You don't need to memorize architectures. You need one repeatable process that turns a vague prompt like "design a chat app" into a design you can defend. This is that process, in seven steps, shown on two very different systems so you can see the same steps produce different answers.

Requirements before boxes

Every box in a diagram should exist because a requirement or a number forced it there. If you can't say which one, remove the box.

Numbers drive decisions

Reads vs writes, data size, latency targets. A rough estimate tells you whether you need a cache, a queue, or nothing at all.

Start simple, then break it

Draw the smallest thing that works. Then ask "what breaks at 10× traffic?" and fix only that. Repeat.

Every choice is a trade-off

There's no right answer, only choices with costs. Saying what you gave up is what separates a good design from a memorized one.

Apply it to any system

Next time you're asked to design something, write these seven headings down and fill them in, in order. Don't draw a box until step 5.

  1. RequirementsWhat must it do (functional)? How well must it do it (non-functional: latency, availability, consistency, scale)? What's out of scope?
  2. NumbersUsers, requests per second, read-to-write ratio, data size per year. Which number is scary?
  3. APIThe handful of calls the client makes. Inputs, outputs, and whether each is a read or a write.
  4. DataWhat entities exist, what's the primary way you look each one up, and does that favour relational, key-value, or wide-column storage?
  5. Simplest architectureClient, load balancer, stateless servers, one database. Walk one read and one write through it end to end.
  6. Break it and fix itWhere does it fall over at the numbers from step 2? Add exactly the component that fixes that: cache, replicas, queue, shards, CDN.
  7. Trade-offsFor each addition, what did it cost? Then say what you'd tackle next with more time.

Check yourself

You're asked to design a news feed. What's the very first thing you say?

A clarifying question, not an architecture. For example: "Is the feed chronological or ranked?" and "Roughly how many users, and how many follow a typical account?" Those two answers change the whole design (fan-out on write vs on read).

Your estimate says 50 reads for every write. What does that suggest?

Reads are the problem to solve first. A cache in front of the database and read replicas will carry most of the load; the write path can stay simple for now.

You added a message queue. What's the trade-off you just made?

You gained resilience and the ability to absorb spikes, but the work is now asynchronous: the user doesn't see the result immediately, you need to handle retries and duplicates, and there's one more system to operate and monitor.
